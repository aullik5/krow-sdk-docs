# 写发版说明

## 一条原则

发版说明是写给**用户**的，不是写给提交历史的。所以组织方式按**影响面**，不按提交顺序。

## 步骤

1. 把变更分成三类，顺序固定：

   - **破坏性变更** —— 用户升级后会坏掉的东西，永远排第一
   - **新增能力** —— 用户现在能做而之前做不到的事
   - **修复** —— 用户之前遇到过的问题

2. 每条只写"对用户意味着什么"，不写实现细节。

   ```
   ❌ 重构了 FooManager 的缓存层
   ✅ 大文件打开速度提升明显（此前每次都全量重扫）
   ```

3. 修复类的每条都要能对上一个"用户可能遇到过的症状"。
   如果一条修复讲不出症状，说明它是内部改动，不该出现在发版说明里。

## 不做

- 不编造版本号 —— 从用户给的信息里取，取不到就问
- 不把每个 commit 都列出来（那是 changelog，不是发版说明）
- 提交信息含糊时，宁可标注"需要作者补充说明"，也不要自己脑补一个用户价值
